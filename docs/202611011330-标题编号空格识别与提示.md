# 标题识别：编号与文字之间空格的识别与提示

## 事由

需求方提出两个问题，并担心"处理不当会误伤"：

1. 标题编号与文字之间**没有空格**（`4.1项目厂址现状`），能否帮助修复
2. 编号与文字之间**多于一个空格**（`1  总论`），能否帮助修复

担心点很具体：以 `10kV电压` 开头的段落，若上一个标题是 `9.3`、下一个标题也符合
递增规则，会不会被误认为标题。

**结论：这个担心成立，而且不需要引入任何"修复"功能就已经在发生。** 经确认，最终
方案是「收紧识别 + 只提示不改内容」，缺空格与多余空格都只出提示，不修改文档。

## 一、实测：误判已经存在

构造「上一标题是 `9.3`」的上下文，直接调用识别用的正则与顺序校验：

| 段落 | 解析出的编号 | 级别 | 顺序合法 | 主循环结论 |
|------|------------|------|---------|-----------|
| `10kV电压引自厂区配电室，…` | `10` | 1 | ✅ | 认成标题 |
| `10kV电压` | `10` | 1 | ✅ | 认成标题 |
| `3.5m标高设配电柜` | `3.5` | 2 | ✅ | 认成标题 |
| `2.3万元` | `2.3` | 2 | ✅ | 认成标题 |
| `10 电气系统采用双回路供电，引自厂区 10kV 配电室，经电缆桥架敷设至各车间。` | `10` | 1 | ✅ | 认成标题（41 字） |
| `9.3设计依据` | `9.3` | 2 | ✅ | 认成标题（正确） |

### 两处根因

```python
# backend/app/domain/ooxml/headings.py
_HEADING_PATTERN = re.compile(r"^(\d+(?:\.\d+){0,4})[\s\t]*(?![)）\.、\-])(.+)$")
```

1. `[\s\t]*` 是**零个或多个**：`10kV` 里的 `10` 后面直接跟 `k`，也被读成「编号 10 + 标题 kV电压」
2. 主循环匹配成功后只做括号平衡检查，**没有长度门槛**。`candidate_max_chars`
   只在「上报跳号」那条支路用，识别主路径没用它

### 后果：不只多一条目录项

`9.3 → 10` 是合法递增，所以 `10kV电压…` 会被接受，`prev_number` 随之变成 `10`。
紧接着真正的 `9.4 设计依据` 会因为 `10 > 9` 被判「顺序非法」，**降级成正文**。

一个段首带数字的正文，会把后面真正的标题踢出目录。

## 二、为什么"缺空格"不是障碍，而是判据

真正的分界线不是"有没有空格"，而是**编号后面紧跟着什么字符**。

```python
def _looks_like_numbered_value(gap: str, rest: str) -> bool:
    if gap:                     # 编号后有空白 → 交给编号链判断
        return False
    if not rest:
        return True
    first = rest[0]
    if not ("\u4e00" <= first <= "\u9fff"):
        return True             # 紧跟字母/数字/符号：10kV、380V、3.5m、1.5%
    return any(rest.startswith(word) for word in _unit_prefixes())
```

| gap（编号后空白） | 紧跟字符 | 例子 | 判定 |
|------------------|---------|------|------|
| 无 | ASCII 字母/数字/符号 | `10kV电压`、`380V`、`3.5m` | 正文 |
| 无 | 中文计量单位 | `2.3万元`、`1.5倍` | 正文 |
| 无 | 汉字标题文字 | `9.3设计依据`、`4.1项目厂址现状` | 标题候选 |
| 有空白 | 任意 | `10 电气`、`9.3 设计依据` | 标题 |

真标题的编号后面是汉字标题文字，不会紧贴 ASCII 字母。这条判据在代码里**原本就存在**，
只是用在别处：

```python
# backend/app/domain/ooxml/headings.py  _looks_like_heading()
if not _STRICT_HEADING_PATTERN.match(text):
    return False
```

它的注释写着「`10kV电源引自…`、`747.08万元` 按正文处理，不上报」。当初只在
**上报跳号**时用了严格模式，识别主循环没用。现在把这条口径挪到识别主路径。

### 中文单位表为什么刻意不收「元」「年」「月」

`1.1年度计划`、`1.1元素分析` 都是合法标题开头。若把「年」「元」收进单位表，
这些真标题会被当成正文，属于典型的过度收紧。表只收**几乎不可能是标题开头**的
多字单位（`万元`、`亿元`、`千米`、`千瓦`、`小时`…），配置在
`config/layout_rules.json` 的 `headings.unit_prefixes`。

## 三、补充的两条门槛

| 规则 | 作用 | 例子 |
|------|------|------|
| 段落长度 > `candidate_max_chars`（60） | 整段说明不该进目录 | `10 电气系统采用双回路供电，引自厂区…` |
| 以 `。`／`；`／`;` 收尾 | 一句话不是标题 | `9.4 本工程电气设计范围包括：…等。` |

冒号**刻意不列入**：项目文档里 `3.1.3 结构设计基本资料：` 这类以冒号结尾的标题很常见，
排除会漏掉真标题。

三条规则都只在段落**没有套标题样式**时生效。作者自己标成标题的段落不做推翻——
文档自带的样式比猜测更可信。

## 四、多空格：先判断是不是「有意对齐」

起初按「编号后不是单个半角空格就提示」实现，在真实文档上跑出 **14 条**提示。
逐条看数据才发现问题：

```
一级标题（styleId 1_1）：
  2 个空白 × 14 处：'1  总论'、'2  建筑'、'3  结构'…
  1 个空白 ×  3 处：'11 机械化设备'、'16 投资估算'、'17 附图'
```

`1  总论` 是「1 个数字 + 2 个空格 = 3 列」，`11 机械化设备` 是「2 个数字 + 1 个空格 = 3 列」，
标题文字都起始于第 4 列——这是不用制表符时的常见对齐手法，不算错误。

因此引入**对齐一致性**判据：

```python
# 每个标题记录「编号长度 + 空白长度」= 标题文字起始列
report.widths.append((level, len(number) + len(gap)))
```

- 同一级别内所有标题的起始列**一致** → 视为有意对齐，不提示
- 不一致 → 说明真的乱了，才提示

再次跑真实文档，一级标题的 widths 实际是 `{3, 4}` 两个值：`10  燃气` 是 2+2=4，
而 `11 机械化设备` 是 2+1=3。**这是文档里真实存在的不一致**（作者手敲空格的疏漏），
所以提示是对的，只是不该刷 14 条。

于是再加一层：**超过 3 处合并成一条**。原因是 `max_issues` 上限 20，逐条列会占满名额，
把需要逐个处理的错误（标题跳号等）挤出去。合并后是：

```
共 14 处标题的编号与标题之间有多余空白，如「1  总论」、「2  建筑」、「3  结构」等。
规范写法是编号后只留一个半角空格。
```

真实文档最终提示从 20 条降到 5 条：

```
「…」被标记为标题样式，但没有可用编号，已按正文处理。          × 2
标题「4.1项目厂址现状」的编号与标题之间缺少空格…                ← 缺空格，逐条
标题「4.2设计依据」的编号与标题之间缺少空格…                    ← 缺空格，逐条
共 14 处标题的编号与标题之间有多余空白…                        ← 多空格，合并
```

缺空格逐条、多空格合并：前者通常零星几处、需要精确定位逐个改；后者是批量问题，
整体替换即可。

## 五、只提示，不改内容

按需求确认，程序**不修改**文档里的空格：

- 缺空格：`4.1项目厂址现状` 保持原样，输出提示，让用户在 Word 里补
- 多空格：`1  总论` 保持原样，输出提示

理由是不对称的代价——漏改一个空格，用户右键「更新域」时自己能发现；误改一处正文，
会把编号和标题文字切错，还会打断编号链，用户很难察觉。

新增问题码与文案：

| 配置项 | 默认 | 含义 |
|--------|------|------|
| `heading.glued_severity` | `warning` | 缺空格 |
| `heading.spacing_severity` | `warning` | 多余空白（可设 `off` 关掉） |

代码位置：

```text
backend/app/domain/ooxml/headings.py
    _looks_like_numbered_value()   # 数值型正文判别
    _unit_prefixes()               # 中文单位表（来自 layout_rules.json）
    _PROSE_TAIL                    # 句子收尾标点
    HeadingReport.widths           # 标题文字起始列，用于对齐判定

backend/app/domain/ooxml/conformance.py
    collect_heading_issues()       # 对齐判定 + 超过 3 处合并
    _spacing_issues()
```

## 七、仍未解决的风险

1. **中文单位表不可能穷尽**。`3.5万元` 能挡住，`3.5万` 挡不住（`万` 没收进表，
   因为 `1.1万向节` 这类可能是标题）。遇到新单位应补进
   `layout_rules.json` 的 `headings.unit_prefixes`，不要改代码判断。
2. **`2.3 万元估算` 这种带空格的数值段落**仍会被认成标题。有空白时无法从形态上
   区分，只能靠编号链。当前未处理。
3. **编号链式纠错依赖顺序**：第一个标题必须是 `1` 开头，否则整篇跳过。这是既有
   设计，本次未改动。
4. 若某文档的一级标题**全部**用 2 个空格且没有两位数编号，对齐判据会认为一致、
   不提示。这属于"整篇统一的排版选择"，符合预期，但严格规范上仍是 2 个空格。
