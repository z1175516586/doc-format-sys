# 文档身份 nodeId 编辑保存后丢失

> 记录时间：2026-11-01 10:35
> 主题：转换产物里的 nodeId 写入位置错误，Word/WPS 编辑保存后身份消失
> 结论：身份原来写在 `customXml` 自定义部件里，Word 另存时整块丢弃；改为写 `word/settings.xml` 的 `w:docVars`（Word 原生文档变量）后，编辑保存可保留。

---

## 1. 现象

转换产物下载下来后，再被用户用 Word/WPS 打开、改字、保存、重新上传，系统认不出这是同一份文档：

- 转换树断了，被当成一份全新文档
- 之前的父节点、历史记录、派生关系全部对不上

而在纯程序流程里（转换完直接查询）身份是正常的。差别只在**中间经过了 Word 的一次打开+保存**。

---

## 2. 原因：写在了 Word 不认的地方

原实现把 nodeId 写在 OOXML 包的一个自定义部件里：

| 项 | 值 |
|---|---|
| 部件 | `customXml/dfsLineage.xml` |
| 配套部件 | `customXml/dfsLineageProps.xml` |
| 关系文件 | `customXml/_rels/dfsLineage.xml.rels` |
| 内容 | `<lineage xmlns="https://doc-format-sys/ns/lineage"><nodeId>…</nodeId></lineage>` |

当时的取舍是「Word 另存时通常会保留 customXml，比改 `settings.xml` 更稳」。这个判断是错的。

`customXml` 是给**内容控件数据绑定**用的容器。Word 在打开文档时会重建自己的 customXml 部件集合，凡是没有被内容控件引用的部件，另存时直接丢弃。我们那份只存了个 `nodeId`、没有任何 `w:sdt` 引用它，正好落进「无用部件」这一类。

### 2.1 实测证据

用 LibreOffice headless 做一次「打开后另存」（等价于一次编辑保存）：

```powershell
soffice --headless --norestore --convert-to docx --outdir out src.docx
```

| 阶段 | customXml 部件 | settings.xml 里有 docVars |
|---|---|---|
| 写入 nodeId 后 | `item1.xml`、`itemProps1.xml`、`_rels/item1.xml.rels`、**`dfsLineage.xml`** | 否 |
| 另存之后 | `item1.xml`、`itemProps1.xml`、`_rels/item1.xml.rels` | 否 |

`dfsLineage.xml` 消失了，身份也就没了。Word 的行为与之一致：这个部件不是它维护的东西，它不会为你保留。

---

## 3. 现在的做法：Word 原生文档变量

参考 `doc-format-sys-0`（旧系统）的 `service/convert_history_service.py`，它用的是 Word 的「文档变量」：

```python
DOCVAR_NAME = "DocHistoryId"
SETTINGS_XML_PATH = "word/settings.xml"
```

写入后的结构：

```xml
<w:settings ...>
  ...
  <w:docVars>
    <w:docVar w:name="DocHistoryId" w:val="abc123"/>
  </w:docVars>
  ...
</w:settings>
```

文档变量是 Word 自己的一等功能：Word 打开时把它们读进内存（宏里可以通过 `ActiveDocument.Variables` 访问），保存时原样写回。WPS 同样支持。因此编辑保存不会丢。

### 3.1 为什么不能像旧代码那样拼字符串

旧实现是这么插入的：

```python
settings_xml = settings_xml.replace("</w:compat>", f"</w:compat>{insert_block}", 1)
```

`CT_Settings` 在 ECMA-376 里是 `xsd:sequence`，子元素顺序是**强制**的，不是一个可以随便放的袋子。`w:docVars` 的合法位置在 `w:compat` 之后、`w:rsids` 之前。一旦文档恰好带有 `rsids`、`mathPr`、`themeFontLang` 等元素，硬塞在 `compat` 后面就会排到它们后面，Word 判定结构非法，打开时提示「发现无法读取的内容，是否修复」。

现实现按 schema 顺序定位：从 `w:docVars` 的合法后继元素里找出第一个存在的，插在它前面；一个都没有就追加到末尾。

```python
_AFTER_DOCVARS = (
    "rsids", "mathPr", "attachedSchema", "themeFontLang", "clrSchemeMapping",
    "doNotIncludeSubdocsInStats", "doNotAutoCompressPictures", "forceUpgrade",
    "captions", "readModeInkLockDown", "smartTagType", "schemaLibrary",
    "shapeDefaults", "doNotEmbedSmartTags", "decimalSymbol", "listSeparator",
)
```

实测写入后（python-docx 生成的底稿）：

```
zoom > proofState > defaultTabStop > characterSpacingControl > savePreviewPicture
     > compat > docVars > rsids > mathPr > themeFontLang > clrSchemeMapping
     > doNotAutoCompressPictures > shapeDefaults > decimalSymbol > listSeparator
     > docId > defaultImageDpi
```

LibreOffice 另存后它自己重排成 `compat > docVars > themeFontLang`，位置依然合法。

### 3.2 存活验证

同一份文档，写入 `DocHistoryId = node-abc-123`，经 `soffice` 另存后回读：

| 方案 | 另存后 nodeId |
|---|---|
| customXml 部件 | **丢失** |
| settings.xml `w:docVars` | 保留，值仍为 `node-abc-123` |

### 3.3 读写策略

| 操作 | 行为 |
|---|---|
| 写 | 只写 `settings.xml` 的 `w:docVars`；同时删除遗留的 `customXml/dfsLineage*` 三个部件和对应 `[Content_Types].xml` override，避免一份文档存在两个互相矛盾的身份 |
| 读 | 先读 `w:docVars`；读不到再回落到 `customXml`，兼容改造前已经产出的历史文档 |
| `settings.xml` 缺失 | 自动补一个最小部件，并在 `word/_rels/document.xml.rels` 里挂上 `settings` 关系、在 `[Content_Types].xml` 里补 Override |

`LineageStamp` 的对外的 `read()` / `write()` 接口没有变化，`HistoryService` 一行没改。

## 5. 遗留与注意

- 改造前已经产出的文档，身份还在 customXml 里，能被读取，但**一旦被 Word 编辑保存仍然会丢**。要彻底保住，需要重新走一次转换，或提供一次「补写身份」的操作。
- 判断标准不是「文件里有没有那段 XML」，而是「Word 保存后还在不在」。以后扩展身份机制时，验收方式统一为：写入 → LibreOffice/Word 另存 → 回读。
- 同类坑：`docProps/custom.xml`（自定义文档属性）也是 Word 会保留的位置，可作为备选；但它会被「文档检查器」清理，稳定性不如文档变量。
