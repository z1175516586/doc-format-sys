# 目录更新域报错与 LibreOffice 并发问题

## 现象

1. 产出文档右键目录「更新域」，Word 提示：

   > Microsoft Word 正在创建目录。请首先将样式库中的标题样式应用于所选文本。

   实际上目录里一个条目都没有，显示「未找到目录项。」
2. 高并发时 LibreOffice 弹出 `soffice.bin 应用程序发生异常` 崩溃对话框。

## 一、目录是怎么生成的

流水线步骤（`backend/app/services/format_service.py` 的 `PIPELINE_STEPS`）：

| 步骤 | 做什么 |
|------|--------|
| `toc_cleanup` | 删掉源文档里旧的目录块（内容控件 / 旧式域目录 / 纯文本目录行） |
| `headings` | 识别标题并套上 `heading 1..4` 样式（带 `outlineLvl`） |
| `toc_insert` | 在第一个一级标题前写「目      录」标题 + TOC 域 |
| `toc_section` | 目录独占一节，正文单独编页码 |
| `save` | 落盘 |
| `engine` | 用 LibreOffice 刷新域（算出真实页码） |

`toc_insert` 写的是**域代码**，不是静态文本：

```
TOC \o "1-3" \h \z \u
```

- `\o "1-3"`：按**大纲级别** 1~3 收集标题（`heading 1..3` 自带 `outlineLvl`）
- `\h`：条目做成超链接
- `\z`：网页视图下不显示页码
- `\u`：同时用大纲级别和样式

「目      录」之后那段 `1 总论 …… 1` 的条目，是 `engine` 步骤里 LibreOffice
刷新后展开的内容，页码由 LibreOffice 排版算出。

## 二、为什么 Word 更新域会报错

### 根因：LibreOffice 把域指令改写成了指向空样式的 `\t`

`engine` 步骤刷新域之后，文档里的指令变成了：

```
TOC \z \u \t "yhl的标题1,1" \h
```

对比两处变化：

| 项 | 我们写的 | LibreOffice 刷新后 |
|----|---------|------------------|
| 收集方式 | `\o "1-3"` 按大纲级别 | `\t "yhl的标题1,1"` 按样式名 |
| 目标样式 | 大纲级别 1~3 | `yhl的标题1` |

实测确认（本机 LibreOffice 26.8）：给它一份指令是 `\o "1-3"` 的文档，
刷新保存后指令一定会被改成 `\t "yhl的标题1,1"`。这不是我们代码里写的
`yhl` —— 全仓库检索不到这个字符串，它来自 `resources/cover_template.docx`
里遗留的自定义标题样式（`styleId=yhl1`，`outlineLvl=0`）。

### 为什么这就报错

`yhl的标题1` 这个样式在最终文档里**一个段落都没用到**（实测正文 0 段），
而真正的标题用的是 `heading 1/2/3`。Word 拿到「按样式名收集」的指令后
去找使用 `yhl的标题1` 的段落，找不到，于是「未找到目录项」，
并提示「请首先将样式库中的标题样式应用于所选文本」。

Word COM 自动化对照实测：

| 文档 | 指令 | 更新域结果 |
|------|------|-----------|
| 原始产出 | `TOC \z \u \t "yhl的标题1,1" \h` | 「未找到目录项。」，1 段 |
| 指令改回 | `TOC \o "1-3" \h \z \u` | 144 条，一/二/三级齐全 |

### 修复

`TocProcessor.normalize_field_instruction()` 把指令规范化回
`TOC \o "x-y" \h \z \u`，并在 `engine` 步骤**刷新之后**强制调用
（无论刷新成功与否）。指令模板抽到 `config/layout_rules.json` 的
`toc.field_instruction`，不再散落在代码里。

```text
backend/app/domain/ooxml/toc.py
    canonical_instruction()           # 读配置生成规范指令
    _iter_field_instructions()        # 按 fldChar 状态机取域指令（不混入 PAGEREF）
    TocProcessor.normalize_field_instruction()
    normalize_toc_instruction(path)   # 落盘版本
```

## 三、关于并发：LibreOffice 能不能并行

### 实测数据（Windows + LibreOffice 26.8）

**格式转换 / 多实例**：每个任务独立进程 + 独立 profile，4 路并行
墙钟 4.12s，串行累计 16.26s，加速比 3.94x —— 这部分能并行。

**域刷新**：

- 同一份文档，冷启动 soffice 单份约 2.5s；常驻实例复用后单份约 0.9s。
- 但**同一实例被两个客户端同时刷新时，时好时坏**：有时 2.68s 双成功，
  有时双双退出码 1 并抛异常。并发跑多份时出现
  `soffice.bin 应用程序发生异常`。

结论：域刷新**不能并行**，因为 soffice 是全局单点，并发会崩。
这不是「配置调大就能解决」的问题。

### 当前做法

`_RefreshGate`（`backend/app/converters/libreoffice.py`）：

- 进程内：`threading.Lock`
- 跨进程：临时目录下的锁文件（`O_CREAT|O_EXCL`，按年龄清理残留）
- 等待超时由 `DFS_LIBREOFFICE_LOCK_TIMEOUT_SECONDS` 控制（默认 600s）
- 超时或引擎异常不让任务失败，降级为「打开时更新」，并写入 warning

实测：4 个请求并发提交，自身耗时严格递增（3.45 → 6.82 → 9.38 → 11.94s），
是标准串行特征，全部成功、无崩溃。

### 更彻底的做法：不下场算页码（当前默认）

写 `w:updateFields` 到 `word/settings.xml`，让 Word / WPS 打开时自己更新域。

实测（把目录页码全改成 `999` 再打开）：

| 文档 | 打开后页码 |
|------|-----------|
| 无 `updateFields` | 仍是 999，Word 不管 |
| 有 `updateFields` | 自动纠正为 1、2、…，条目 144 条 |

也就是说，**服务器端完全可以不跑 LibreOffice 刷新**，页码由客户端排版引擎
算，最准、零并发瓶颈。代价是打开瞬间 Word 会更新域（大文档有短暂等待）。

```text
backend/app/domain/ooxml/update_fields.py
    UpdateFieldsFlag      # 读写 w:updateFields，按 CT_Settings 顺序插入
    enable_update_fields(path)
```

配置在 `config/layout_rules.json` 的 `toc` 段：

| 键 | 默认 | 含义 |
|----|------|------|
| `update_fields_on_open` | `true` | 写 `w:updateFields`，Word 打开时算页码 |
| `server_refresh_fields` | `false` | 是否在服务器端跑 LibreOffice 预刷新 |
| `levels` | `"1-3"` | 纳入目录的标题层级；文档到五级标题时改 `"1-5"` |
| `field_instruction` | `TOC \o "{levels}" \h \z \u` | 最终写入的域指令 |
| `placeholder_text` | `目录将在打开文档时自动更新` | 未刷新时域里的占位文字 |

前两项互斥，同时为 `true` 会被 `ConvertOptions` 与 API 层拒绝。

`engine` 步骤的返回值会说明走了哪条路：`reason: server_refresh_disabled` 表示
服务端没刷新（`skipped: true`），`update_fields: true` 表示已交给客户端。
落盘后再补写一次 `updateFields`，因为 LibreOffice 整包回写会覆盖 `settings.xml`。

端到端实测（`server_refresh_fields=false`，完全不碰 soffice）：
Word 打开即生成 144 条目录、页码 1/1/1/…、层级 1-3，图片 4 张保留。

### 五级标题

有的文档标题到五级，链路已打通：

- `headings.max_level` = 5，五级标题套 `heading 5`（`outlineLvl=4`），不再回落到四级
- `toc 1..5` 样式均已预置，字体（宋体 / Times New Roman 四号）与顶格规则按级别覆盖
- `levels` 改 `"1-5"` 即可纳入四级、五级

实测：同一文档 `\o "1-3"` 得 144 条；改 `\o "1-5"` 得 158 条
（多出 14 个四级标题），Word 报告 `UpperHeadingLevel=1, LowerHeadingLevel=5`。

## 四、如果要支持大量并发请求

当前默认走第 1 条：`server_refresh_fields=false` + `update_fields_on_open=true`，
后端只剩 OOXML 处理，worker 可以开到 CPU 核数，没有全局单点。

按代价从低到高：

1. **关掉服务器端域刷新**（当前默认）。页码由客户端算，无单点、无排队。
2. **域刷新独立队列**：把 `engine` 步骤拆成异步后置任务，单 worker 串行消费，
   完成后再通知前端。请求不被阻塞，但交付时间变长。
3. **多实例池**：N 个常驻 soffice（各自独立 profile 与端口），每实例配一把锁，
   崩了自动重启补位。这是 JODConverter / unoconv 的标准做法，能真并行，
   但要处理实例健康检查与内存占用（每个 soffice 常驻约 100–200MB）。

`_RefreshGate` 保留着，是为了第 2、3 条或临时打开 `server_refresh_fields` 时
不会重新踩崩溃；默认路径根本不进这个闸门。

## 五、两种方式并存：前端单选 + 排队提示

上文的两个开关暴露到界面，但**是互斥单选**，不是多选。

二者是同一个决策的两种实现：服务端算完落盘后，客户端打开时又会重算一遍。
同时开启没有任何额外收益，只是白占全局单点的排版引擎（还要排队），
并且让「是否需要告警」的判断失去意义。所以从界面到 Schema 都强制二选一。

| 选择 | 效果 | 实测 |
|------|------|------|
| 打开文档时自动更新（默认） | 不碰 soffice，写 `w:updateFields` | `engine` 跳过，`updateFields=true`，目录条目由 Word 生成 |
| 服务器端预刷新 | LibreOffice 算好页码落盘，不写 `updateFields` | `refreshed=true`，143 条，页码已确定 |

两道防线：

```text
前端  Radio.Group（constants/app.ts 的 TOC_PAGE_SOURCE_OPTIONS）
        只提交 toc_page_source 对应的一个 true，另一个显式 false
Schema ConvertOptions._single_page_source()
        两个都为 true 直接 ValueError，杜绝别的调用方造出矛盾状态
API   _build_options → _resolve_page_source()
        两个都为 true 返回 400；只传一个时另一个强制收敛为 false
```

最后一条尤其重要：如果只传 `server_refresh_fields=true`、让另一个回落到配置
默认值 `true`，就会静默造出矛盾组合。实测报文：

```json
{"code":"validation_error","message":"update_fields_on_open 与 server_refresh_fields 只能选一个"}
```

表单字段：`update_fields_on_open`、`server_refresh_fields`（`POST /api/v1/documents/convert`，
同步与异步两个接口都支持）。都不传则回落到 `config/layout_rules.json` 的默认值。

引擎不可用时（未装 LibreOffice），「服务器端预刷新」单选会被禁用并提示原因，
已选中的也会自动回落到客户端更新，不会提交一个注定降级的任务。

### 排队时要让用户看得见

引擎是全局单点，勾了「服务器端预刷新」的请求必然要排队。之前的表现是进度条
停在「刷新目录页码」一动不动几分钟，用户以为程序死了。

现在闸门会在两个时刻上报，经 SSE 推到前端：

```text
RefreshGate.acquire(on_phase)
    非阻塞抢一次 →（失败）on_phase("waiting", "前面有任务正在刷新目录页码，已排队等待排版引擎空闲")
    抢到之后     → on_phase("running", "已取得排版引擎，正在计算目录页码")
```

进度事件带 `data.engine_phase`（`waiting` / `running`）与 `data.waiting`：

```json
{"type":"progress","step":"engine","percent":72,"message":"前面有任务…",
 "data":{"engine_phase":"waiting","waiting":true}}
```

前端收到 `waiting` 时按钮显示「排队等待中」，并在下方给出说明条；
收到下一个事件即恢复常规进度。文案统一在 `layout_rules.json` 的
`toc.engine_messages` 与前端 `constants/app.ts` 的 `TOC_PAGE_SOURCE`。

### 踩到的坑：回调不能存在单例上

`_RefreshGate` 是进程级单例。第一版把 `on_phase` 存成实例字段，结果并发时
互相覆盖：A 任务在排队，B 任务刷新完成走 `release()` 顺手把回调清空，
A 拿到锁后**收不到 `running`**，前端就永远停在「等待中」。

现在 `on_phase` 一律按调用传参（`acquire(on_phase)` → `_acquire_file_lock(..., on_phase)`），
实例上不再保留任何 per-call 状态。

实测两个任务并发，被抢占的一方事件序列为
`waiting → running`，先拿到的一方只有 `running`；四种勾选组合均通过。
